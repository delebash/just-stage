## Steps (each with its standard)

1. **Ship the wheel** - Blender's extension wheels
   (https://docs.blender.org/manual/en/5.3/advanced/extensions/python_wheels.html): the manifest's `wheels` lists
   `./wheels/<wheel>`; `build.py` puts the wheel there (made per machine, gitignored, as generated data); Blender
   installs it when the extension is enabled at startup (`addon_utils._initialize_extension_repos_post_addons_restore`
   -> `extensions_refresh`), and a script that enables the add-on itself calls Blender's own
   `addon_utils.extensions_refresh(addon_modules_pending=[...])` first ("needed so wheels can be setup before the
   add-on is enabled" - its docstring, Blender 5.3). Test: `import dna, riglogic` inside the test run.
2. **Research before authoring** (the research skill; RESEARCH §14.7 and `2026-11-05-research-face-animation.md`
   read first): how to author a minimal valid face DNA with none of Epic's mapping values (S8 gap 18-a1) - OpenRigLogic's
   own `python/dna/examples/demo.py` and `test_dna.py` first, then Poly Hammer's GPL-3 `character-dna-addon` (the plan:
   "weighed first, before our own DNA tooling").
3. **The DNA (design, mine, 2026-11-08 - to attack before building):**
   - Definition: MetaHuman's 174 GUI and 251 expression raw control names (the spec §2.3, names only - read per machine
     from the user's archetype by the tool, as Manny's places were; `skm-face-definition-names.json` the record); our
     joints by MetaHuman's names where ours exist (`FACIAL_C_FacialRoot`, `FACIAL_C_Jaw`, `FACIAL_L/R_Eye`,
     `FACIAL_C_TeethUpper`, `FACIAL_C_TeethLower`, `FACIAL_C_Tongue1-4`), mirrored into the skeleton's armature as
     children of `head`; blend-shape channels by the raw expressions' names (`CTRL_expressions.<x>` -> channel `<x>`).
   - Behaviour, all values ours (clean-room: names only): GUI -> raw by each control's own range (a `.ty` 0..1 control
     to its expression 1:1; a two-way control split at 0); raw -> channel 1:1 (RigLogic drives a channel from one input);
     `jawOpen` / `jawLeft` / `jawRight` / `jawFwd` -> `FACIAL_C_Jaw`'s rotation and translation, `eyeLook*` -> the eye
     joints, our degrees measured on our jaw and eyes.
   - The shapes behind the channels, in Blender: each expression's shape key made from our ARKit 52 - one-to-one where the
     names match (browDownL -> browDownLeft, eyeBlinkL -> eyeBlinkLeft, eyeCheekRaiseL -> cheekSquintLeft,
     mouthCornerPullL -> mouthSmileLeft, mouthCornerDepressL -> mouthFrownLeft, noseWrinkleL -> noseSneerLeft, ...); a
     shape split by smooth region masks where MetaHuman's is finer (mouthLipsPurse UL / UR / DL / DR = mouthPucker by
     quadrant, mouthFunnel the same, mouthPress U / D, browRaiseIn L / R from browInnerUp); the rest at 0 and listed
     until a scanned set gives them (Q-RIG-1).
   - Runtime: the character's DNA evaluated by RigLogic when its controls change (a depsgraph / frame handler, as Poly
     Hammer's), outputs written to the shape keys and the face bones - "never hand-made drivers" (the data model §2).
   - Attack: (A) does it change a user decision? No - names per item 10, DNA + RigLogic per N4, ARKit 52 kept beside.
     (B) Simpler: drive our ARKit keys straight from MetaHuman curves by a table, no DNA? That is a mapping file of ours
     (item 17 rules it out) and has no PSD / wrinkle layers for later. (C) Region-split shapes are an authoring step of
     ours (NOT STANDARD detail; the standard is sculpted per-expression shapes, which we lack) - measured at the gate
     against HD Aaron's own fine shapes. (D) The jaw as a joint replaces the teeth's baked keys (Q-RIG-5) - every caller
     of `face_units.add_to_teeth` and `JAW_UNITS` changes in the same step (blast radius to grep then).
4. Correctives and wrinkle maps (their sources are Q-RIG-4 / research), later.
